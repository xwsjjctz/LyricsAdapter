# 产品收敛与桌面交互规划

更新日期：2026-09-16。来源：本轮产品讨论及源码核对。

本文区分已经确定的方向、待验证的交互方案和本次实现范围。规划中的后续事项不表示已经实现，也不是一次性重构全部功能的任务。

## 1. 产品方向与功能取舍

以本地收藏、在线发现与播放、同步/逐字歌词和 Focus Mode 为主要体验。精简云端文件管理；不要仅为了减少页面数量，把完整功能堆进狭窄面板。

| 功能 | 讨论结果 | 实现状态 |
| --- | --- | --- |
| 本地导入、播放、搜索、歌词、系统媒体控制 | 保留 | 本次不改 |
| 在线搜索、播放、平台歌单 | 保留 | 本次不改 |
| 在线下载到本地 | 重要能力，保留；与歌词离线收藏绑定 | 本次不改，离线闭环后续核验 |
| 完整元数据编辑 | 保留，不缩减为仅编辑歌词 | 本次不改 |

“移除不删音频”限定于曲库移除操作，不代表禁止用户通过元数据编辑明确保存修改到音频文件。

## 2. 曲库移除与缓存边界

已统一使用“从曲库移除”表达动作，处理持久化记录、选择状态、当前播放索引和应用缓存。

- 原音频文件保持存在。
- 清理缓存前检查其他记录、来源及当前播放的引用；不能删除仍在使用的数据。
- 评估移除后的短时撤销，避免每次移除都打断操作。
- 自动扫描的网络来源需要明确“移除/隐藏”的持续性，防止下一次刷新立即恢复条目。
- 移除正在播放的歌曲：暂停、取消待触发的自动播放，选中相邻的下一首存活歌曲；末尾则选前一首。进度归零，全部移除后无选中歌曲。移除其他来源不打断播放。
- 缓存或 blob 仍被其他曲库引用时保留；持久化失败时保留缓存，交由现有运行时与退出保存机制重试。
- 本次歌曲菜单的管理范围为本地曲库与在线队列。WebDAV 自动扫描列表和平台歌单仍由原来源管理，不新增远端删除或永久隐藏规则。

## 3. 编辑模式、鼠标与批量操作

批量需求主要是移除歌曲，无需围绕批量标签编辑扩展功能。

方向：利用桌面端右键菜单、键盘与直接拖动。按最新反馈，移除行尾“⋯”，鼠标入口只保留右键；保留键盘菜单键及 Shift+F10。

拖拽采用鼠标按下后移动超过距离阈值触发，不要求按住等待。显示明确插入位置。区分自定义排序与按歌名/专辑等规则排序，避免在规则排序下产生不可解释的拖动结果。

### 最新讨论方向：歌曲菜单 + 当前列表多选

此前仅记录规划；本轮用户要求执行剩余移除项，已按以下交互实现。

- 常态保持单击歌曲播放，顶部不再常驻铅笔编辑按钮或另一个“选择”按钮。
- 右键歌曲打开操作菜单：编辑歌曲信息、选择多首歌曲、从曲库移除。
- 元数据编辑直接打开现有完整编辑器，移除其行内独立按钮，不移除编辑能力；单曲移除也收进菜单。
- 点击“选择多首歌曲”后关闭菜单，在当前列表进入选择状态，不把勾选操作放进层层子菜单。
- 预选触发菜单的歌曲；点击行主体切换选中，不触发播放。
- 临时操作条显示已选数量、全选、移除所选、完成；完成或 Esc 退出选择。“完成”只结束选择，不表示保存元数据。
- 多选时暂时停用右键菜单及排序拖拽，避免选择、播放、重排相互冲突。
- 普通状态下直接拖拽排序；只有放下到歌曲行才提交，取消拖动不改变顺序。

### 列表最左列

用户说明该列主要是为编辑状态的复选框协调布局，没有独立的序号需求。已移除常态序号列和“#”表头，让封面成为歌曲行的起点。

多选状态把封面位置临时替换为复选框，不新增一列，保持歌名、歌手及其他字段的位置稳定。全选放在临时操作条；普通状态继续用行高亮表达播放状态。失效歌曲也允许选中并从曲库移除。

### 先前比较过的方案

讨论过独立批量处理面板，以及单击选择、双击播放的完整桌面列表方案。最新方向优先采用上面的菜单入口和原列表多选，不把这些早期候选同时叠加到界面。

用户观察到 QQ 音乐采用批量入口后打开另一份列表处理，Apple Music 在其使用场景中没有明显的批量入口。这是产品讨论中的观察，不作为所有版本/平台的功能断言。

## 4. 搜索与添加音乐

现状：搜索为跨本地、已加载云端与在线来源的全局搜索，不筛选下方曲库列表。本地/云端结果每组最多 8 首，没有查看全部入口；选择结果会播放歌曲。

后续区分“找歌听”与“在当前曲库筛选后整理”的需求。待讨论范围选择、完整结果入口，以及关闭结果是否保留关键词。不在本次更改搜索范围、搜索状态或播放动作。

本地导入保留直接选择文件和拖入方式。后续评估明确的“添加音乐”文字、重复文件/完成反馈及按钮强调程度。

## 5. 逐字歌词与离线收藏

产品要求：在线下载应把可获取的音频和逐字歌词作为一份离线收藏保存。未来即使无法连接 QQ/网易，已经保存的收藏也应能继续显示逐字歌词，不能只依赖短期在线缓存。

源码现状：

- `usePlayerController.enrichProviderTrackLyrics` 会通过歌曲来源请求歌词，在线搜索播放和歌单播放已有逐字歌词补全路径。不是“在线播放目前不能显示逐字歌词”。
- 实际是否有逐字数据取决于来源返回；不能凭空生成平台未提供的逐字时间。
- `useOnlineMusicIntegration.handleOnlineDownload` 获取歌词并尝试写入 `wordLyrics` / `wordLyricsFormat`，本地导入有读取对应标签的路径。
- 这些路径存在，不代表已经验证每种文件/音质的完整离线闭环；本次不改歌词或下载实现。

后续验收：下载有逐字歌词的 QQ/网易歌曲，重启、断网、清除在线歌词缓存后仍能显示；重新导入下载文件时能够恢复逐字信息。覆盖 MP3/FLAC、来源身份、写标签失败、平台仅返回逐行或无歌词的情形。应明确失败反馈与降级策略，不能把未保存逐字歌词的结果默认为完整收藏成功。

## 6. 网络曲库：事实、选择与待验证项

### 协议与其他实现

PROPFIND 属于 WebDAV，不属于 SMB。WebDAV 的普通目录属性（路径、大小、修改时间等）不能等同于音频内嵌的歌名、歌手、封面和歌词；SMB 通过自身的目录枚举及文件读取访问这些内容。

核对的公开资料：

- [Symfonium SMB 官方说明](https://docs.symfonium.app/wiki/providers/samba-smb-v2-v3-media-provider-configuration/)：首次扫描使用标签解析器读取媒体元数据，可能耗时并传输大量数据；保存标签缓存，后续同步及中断恢复复用缓存。不是仅列目录、等播放才获取全部标签。
- [foobar2000 2.25 官方发布说明](https://www.foobar2000.org/releasenotes-2.25)：提供 SMB/FTP 曲库索引。该说明不足以确定其逐字段懒加载、读取量或并发策略，不作进一步推断。
- [Navidrome 官方入门说明](https://www.navidrome.org/docs/getting-started/)：音乐服务器在后台扫描曲库。服务端索引是另一种架构，不能与客户端直接读 SMB/WebDAV 混为一谈。
- [WebDAV RFC 4918](https://www.rfc-editor.org/rfc/rfc4918.html#section-9.1)：PROPFIND 获取资源属性。
- [HTTP Range RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2)：服务端允许忽略 Range，需验证所用 WebDAV 服务的部分读取行为。

### 当前实现与候选收缩方向

当前实现已按 provider 区分，不能把 123pan 的专属流程描述成所有 WebDAV 连接的通用负担。`providerConfig.ts` 中，123pan 启用 `useMetadataFolder` 与 `allowWrite`；通用 WebDAV 两者均为 false。`useWebDAV.ts` 的 `Metadata/` 索引、分块及相关写回路径受这些配置控制；只读设置还会覆盖写入权限。

本次保留这套分流及 123pan 适配，不删除远端索引、迁移、修复或缓存写回。此前“收缩云端索引”的表述仅保留为可讨论方向，不作为已批准移除项。

内网没有服务商限流，也仍受磁盘、网络带宽、文件布局、图片处理和本机解析能力限制。现有冷读路径通常先读每首约 1 MiB 文件头，大标签/封面再补读。假设 1,000 首都需要这一步，约 1 GiB；在假设的 100 MiB/s 下仅传输约 10 秒。这是量级估算，不是基准测试。

候选方向：目录/本机缓存先形成可用列表；后台逐步读取并保存音乐标签；当前播放优先；封面等按需补齐；采用有界并发。这样可以取消部分专属远端维护，同时保留基本的体验优化。仅在播放时读取所有标签会影响未播放歌曲的搜索、分类和排序，需要实际权衡。

尚未决定：

- 是否退出远程索引写回，以及现有远程缓存如何兼容读取。
- SMB 通过系统挂载路径接入，还是在应用中实现连接管理。
- 内网 WebDAV/SMB 的冷启动、热启动、首次可播放和后台索引耗时目标。

先用真实曲库比较，再决定方案；本次不实现 SMB、不调整并发、不改变 WebDAV 元数据策略，也不宣称网络来源已经完全只读。

## 7. Focus Mode 与整体布局

位置参数、修复前实测值和首轮横向位移修复记录见 [Focus Mode 位置实现记录](focus-mode-layout.md)。

保留现有 Focus Mode 进出动画、macOS 红绿灯旁蓝色按钮及 Windows 对应入口的价值。蓝色按钮可保留探索感，但应评估首次可见提示及快捷键，避免只依赖用户猜测。

候选演进：精简曲库界面 + Focus Mode + Focus Mode 内可临时展开的轻量歌曲栏。控制栏的歌曲列表按钮负责临时换歌，蓝色按钮仍负责切换专注状态。

- 先明确侧栏是“当前播放队列”还是“完整曲库”；两者职责不同。
- 展开时优先让封面让出空间、平移和重排歌词，不把所有元素等比缩小。
- 保持歌词可读字号；小窗口评估覆盖式面板。
- 完整元数据编辑、搜索下载和设置不必全部挤进窄栏。
- “删除 Focus Mode 以外全部页面”保留为探索提案，未决定执行。先验证轻量歌曲栏是否足以覆盖常用换歌行为。

## 8. 第一阶段实现：屏蔽音频上传

- 隐藏全局搜索结果和在线浏览页的上传及上传音质菜单。

- 保留原上传函数、参数、界面分支、协议/IPC 和翻译，便于后续恢复或评估删除。

## 11. 第二阶段实现：曲库移除与歌曲菜单

- 移除顶部铅笔按钮、其悬停删除菜单、行内独立编辑/移除图标，以及最左序号/选框专用列。
- 本地曲库和在线队列通过右键打开歌曲菜单。保留完整元数据编辑入口；所有可管理条目提供“选择多首歌曲”和“从曲库移除”。
